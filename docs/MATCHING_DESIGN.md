# Matching Design

## 1. 设计目标

Match Agent 的目标不是把简历关键词和岗位关键词做简单匹配，而是把岗位需求转成岗位画像，再用候选人人才画像进行可解释匹配。

匹配结果必须回答：

- 为什么推荐这个候选人。
- 候选人哪里匹配。
- 候选人哪里有风险。
- 面试时应该验证什么。

## 2. 输入与输出

输入：

- HR 自然语言岗位需求。
- 候选人人才画像。
- 候选人结构化简历。
- 匹配权重。

输出：

- 岗位画像。
- 候选人推荐列表。
- 总匹配分。
- 分项得分。
- 推荐理由。
- 风险点。
- 建议面试问题。

## 3. 岗位画像

HR 输入示例：

```text
我们想招一个 3 年左右经验的产品经理，做 B 端 SaaS，要求逻辑强、沟通好，最好懂数据分析，能推动研发落地。
```

岗位画像结构：

```json
{
  "title": "产品经理",
  "seniority": "3年左右",
  "industry": "B端SaaS",
  "responsibilities": [
    "需求分析",
    "产品方案设计",
    "推动研发落地"
  ],
  "requiredSkills": [
    "产品设计",
    "需求分析",
    "跨团队沟通"
  ],
  "preferredSkills": [
    "数据分析",
    "B端SaaS经验"
  ],
  "requiredCapabilities": [
    "logicAbility",
    "communicationAbility",
    "executionAbility"
  ],
  "careerPreferenceSignals": [
    "偏好B端业务",
    "能接受跨团队协作"
  ],
  "missingFields": []
}
```

## 4. 匹配权重

沿用原始设计的初版权重：

| 维度 | 权重 |
| --- | --- |
| 经验匹配 | 30% |
| 技能匹配 | 30% |
| 画像匹配 | 25% |
| 职业倾向 | 15% |

总分计算：

```text
总分 = 经验匹配 * 0.30
     + 技能匹配 * 0.30
     + 画像匹配 * 0.25
     + 职业倾向 * 0.15
```

MVP 阶段建议总分使用 0-100。

## 5. 分项评分规则

### 5.1 经验匹配

关注：

- 行业经验。
- 岗位经验。
- 工作年限。
- 项目复杂度。
- 业务场景相似度。

高分信号：

- 做过类似行业或岗位。
- 项目职责与岗位职责高度重合。
- 有可验证结果。

低分信号：

- 缺少相关行业或岗位经验。
- 经历明显偏离岗位要求。
- 只有边缘参与，没有核心职责。

### 5.2 技能匹配

关注：

- 必备技能覆盖。
- 加分技能覆盖。
- 工具和方法论。
- 技能使用深度。

高分信号：

- 多个必备技能有项目证据。
- 技能不是只写在标签里，而是出现在真实经历中。

低分信号：

- 只出现技能关键词，没有使用场景。
- 缺少岗位硬性技能。

### 5.3 画像匹配

关注：

- 岗位要求的能力维度。
- 候选人的能力评分和证据。
- 能力置信度。

示例：

- 岗位要求强逻辑，则重点看 `logicAbility`。
- 岗位要求推动落地，则重点看 `executionAbility` 和 `communicationAbility`。
- 岗位要求带团队，则重点看 `leadershipAbility`。

低置信度处理：

- 如果能力评分高但置信度低，应降低匹配信心。
- 如果岗位关键能力缺少证据，应生成面试问题。

### 5.4 职业倾向匹配

关注：

- 行业偏好。
- 岗位方向。
- 工作方式。
- 地点和稳定性。
- 成长诉求。

高分信号：

- 候选人目标方向与岗位一致。
- 候选人偏好的工作方式与岗位环境一致。

风险信号：

- 候选人明确不偏好该行业或岗位类型。
- 频繁转向且原因不清。
- 目标方向与岗位明显不一致。

## 6. 推荐结果结构

```json
{
  "candidateId": "candidate_001",
  "matchScore": 82,
  "scoreBreakdown": {
    "experience": 78,
    "skills": 85,
    "profile": 88,
    "careerPreference": 70
  },
  "matchReasons": [
    "候选人有 B 端产品项目经历，与岗位业务场景接近",
    "逻辑能力和执行能力证据较充分",
    "简历和访谈均体现跨团队推进经验"
  ],
  "risks": [
    "数据分析能力有标签但缺少具体项目证据",
    "职业倾向中对行业偏好表达不够明确"
  ],
  "interviewQuestions": [
    "请候选人具体说明一次使用数据分析支持产品决策的案例",
    "请追问候选人是否愿意长期深耕 B 端 SaaS 场景"
  ]
}
```

## 7. 推荐解释规则

推荐解释必须：

- 对应岗位要求。
- 引用候选人证据。
- 区分强匹配和弱匹配。
- 标记不确定项。
- 避免空泛评价。

不推荐：

> 候选人综合素质优秀，适合该岗位。

推荐：

> 候选人在 XX 项目中负责需求分析和研发推进，与岗位中“推动研发落地”的要求匹配；但数据分析能力只有技能标签，缺少具体项目证据，建议面试追问。

## 8. 风险点生成

风险点来源：

- 岗位关键要求缺少证据。
- 候选人能力评分低。
- 候选人能力评分置信度低。
- 职业倾向与岗位不一致。
- 简历经历断层或频繁变化。

风险点格式：

```json
{
  "risk": "数据分析能力证据不足",
  "reason": "岗位要求数据分析能力，但候选人简历中仅出现技能标签，未提供项目案例",
  "severity": "medium",
  "suggestedQuestion": "请候选人说明一次用数据分析影响产品决策的案例"
}
```

## 9. 面试问题生成

面试问题应围绕：

- 关键岗位要求。
- 匹配分低的维度。
- 低置信度高影响项。
- 简历与画像不一致之处。
- 候选人风险点。

问题类型：

- 经历验证：确认候选人是否真的做过。
- 深度追问：确认贡献和思考过程。
- 风险验证：确认不确定项。
- 职业倾向：确认稳定性和偏好。

## 10. 排序规则

MVP 推荐排序：

1. 按总分排序。
2. 总分相近时，优先关键能力匹配度更高者。
3. 关键能力相近时，优先风险更少者。
4. 风险相近时，优先证据置信度更高者。

## 11. 不应做的匹配

禁止：

- 因年龄、性别、婚育、籍贯等因素做推荐或排除。
- 只因学校或公司光环给高分。
- 只因关键词缺失就完全否定候选人。
- 在缺少证据时给出确定判断。
- 把模型推测当事实。

## 12. 后续演进

MVP 后可扩展：

- 向量检索召回候选人。
- 岗位与候选人双向匹配。
- HR 反馈反哺匹配权重。
- 面试结果反哺人才画像。
- 不同行业定制权重。
- 多模型交叉评估推荐质量。

# MVP Roadmap

## 1. 路线原则

AI Talent Agent 不建议一开始就做完整双边招聘平台。

推荐原则：

- 先验证候选人侧画像质量。
- 再验证简历生成价值。
- 最后接入 HR 侧匹配。
- HR 侧先兼容现有工作流，再考虑深度系统集成。
- 每个阶段都要有可验收产物。

核心路线：

```text
文档完善 -> 候选人侧闭环 -> 简历生成 -> HR 匹配闭环 -> 数据反馈优化
```

## 2. 阶段 0：文档完善

目标：

- 明确产品定位。
- 明确人才画像体系。
- 明确 AI 访谈机制。
- 明确 Agent 输入输出。
- 明确匹配规则。
- 明确 MVP 范围。

交付物：

- `PRODUCT_BRIEF.md`。
- `PRD.md`。
- `TALENT_PROFILE.md`。
- `INTERVIEW_DESIGN.md`。
- `AGENT_DESIGN.md`。
- `MATCHING_DESIGN.md`。
- `HR_COMPATIBILITY.md`。
- `MVP_ROADMAP.md`。

验收标准：

- 产品边界清楚。
- MVP 做什么和不做什么清楚。
- 每个 Agent 的输入输出清楚。
- 人才画像评分和证据机制清楚。
- 匹配算法和解释机制清楚。
- HR 输出材料和传统工具兼容策略清楚。

## 3. 阶段 1：候选人侧简历解析

目标：

- 用户可以上传简历并获得结构化简历数据。

功能：

- PDF / Word 上传。
- 文本提取。
- Resume Agent 结构化解析。
- 解析结果展示。
- 用户校对和修正。

验收标准：

- 能解析至少 5 份不同格式简历样本。
- 能提取基础信息、教育经历、工作经历、项目经历和技能标签。
- 用户能看到和修改解析结果。
- 解析错误不会直接污染后续画像。

## 4. 阶段 2：AI 访谈

目标：

- AI 根据简历上下文追问，并抽取可用于画像的事实。

功能：

- 访谈聊天界面。
- Interview Agent 问题生成。
- 多轮对话状态管理。
- 事实抽取。
- 画像证据缺口识别。

验收标准：

- 至少支持 3 轮上下文相关追问。
- 问题能引用候选人简历中的具体经历。
- 回答能抽取为结构化事实。
- 系统能判断哪些画像维度证据不足。

## 5. 阶段 3：人才画像

目标：

- 基于简历和访谈生成可解释的人才画像。

功能：

- Profile Agent。
- 8 个能力维度评分。
- 优势和风险生成。
- 职业偏好生成。
- 推荐岗位方向。
- 证据和置信度展示。

验收标准：

- 每个能力维度都有评分、解释、证据和置信度。
- 画像结论不能脱离简历或访谈事实。
- 低置信度结论被明确标记。
- 用户能理解为什么得到这些结论。

## 6. 阶段 4：简历生成

目标：

- 基于人才画像生成不同用途的简历版本。

功能：

- Resume Builder Agent。
- ATS 版简历。
- HR 版简历。
- 简历预览。
- 复制或导出。

验收标准：

- 同一候选人能生成至少 2 种版本简历。
- 简历内容来自真实经历和访谈事实。
- 不编造量化结果、项目、学历和公司。
- 用户认为简历版本比原始简历更清晰。

## 7. 阶段 5：HR 匹配

目标：

- HR 可以输入岗位需求，并获得候选人推荐。

功能：

- 岗位需求输入。
- 岗位画像生成。
- Match Agent。
- 候选人评分。
- 推荐列表。
- 匹配详情。
- 风险点和面试问题。
- 候选人一页摘要。
- Excel / CSV 导出。
- 邮件和协作工具转发摘要。

验收标准：

- HR 能用自然语言创建岗位需求。
- 系统能生成岗位画像。
- 系统能对候选人进行排序。
- 每个推荐包含总分、分项得分、理由、风险和面试问题。
- HR 能把候选人摘要和面试问题复制或导出到现有工作流中。

## 8. 暂不做范围

MVP 不做：

- ATS 深度 API 集成。
- 企业复杂权限。
- 自动投递。
- 自动联系候选人。
- 付费系统。
- 背调。
- 大规模候选人检索。
- 多租户招聘流程管理。
- 手机 App。

## 9. 研发前置清单

进入开发前，需要确认：

### 9.1 产品问题

- 第一版是否确认优先做候选人侧。
- 第一版是否需要 HR 侧完整页面，还是只做内部 demo。
- 简历生成是否只做 ATS 和 HR 两个版本。
- HR 侧是否优先支持 Excel / CSV、邮件、飞书/企业微信摘要等兼容输出。
- 是否需要用户登录。

### 9.2 技术问题

- 前端框架。
- 后端框架。
- 数据库。
- 文件存储。
- LLM Provider。
- 文档解析方案。
- 导出格式方案。

### 9.3 数据问题

- 是否准备真实或脱敏简历样本。
- 是否准备岗位 JD 样本。
- 是否需要手工标注画像结果作为评测集。

### 9.4 评测问题

- 如何判断简历解析质量。
- 如何判断访谈问题质量。
- 如何判断画像准确性。
- 如何判断简历生成是否可用。
- 如何判断 HR 推荐是否有价值。
- 如何判断 HR 导出材料是否能进入现有工作流。

## 10. 推荐默认技术路线

如果目标是快速做原型，推荐：

- Next.js 全栈。
- SQLite 起步，后续迁移 PostgreSQL。
- 本地文件存储起步。
- LLM Provider 先抽象为接口。
- Prompt 和 JSON Schema 独立管理。
- Agent 日志必须保留。
- HR 侧先做导出和复制，暂缓第三方 API 集成。

推荐目录：

```text
.
├── app/
├── lib/
│   ├── agents/
│   ├── parsers/
│   ├── prompts/
│   └── schemas/
├── docs/
└── README.md
```

如果项目进入多人协作或更正式研发，再扩展为：

```text
.
├── apps/
│   ├── web/
│   └── api/
├── packages/
│   ├── agents/
│   ├── database/
│   ├── prompts/
│   └── schemas/
├── docs/
└── README.md
```

## 11. 下一步建议

文档完善后，不建议马上全量开发。

建议先做三个轻量验证：

1. 准备 5 份简历样本，手工跑一遍画像流程。
2. 准备 3 份岗位 JD，手工跑一遍匹配流程。
3. 根据结果修订 `TALENT_PROFILE.md`、`INTERVIEW_DESIGN.md` 和 `MATCHING_DESIGN.md`。
4. 用导出的候选人摘要、Excel / CSV 和面试问题模拟一次 HR 真实协作流程。

等画像、访谈和匹配标准稳定后，再进入工程实现。

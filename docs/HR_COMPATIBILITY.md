# HR Compatibility Design

## 1. 设计目标

AI Talent Agent 不应要求 HR 放弃现有招聘工具和工作方式。

更合理的定位是：

> AI Talent Agent 是兼容 ATS、招聘平台和办公协作工具的“候选人理解层”。

它的核心创新是通过简历解析、AI 访谈和人才画像更深度地理解候选人；但对 HR 的交付形态，应尽量保持传统、熟悉、可复制、可导出、可转发。

## 2. 为什么需要兼容传统 HR 流程

如果产品只强调“AI 人才画像”和“新招聘范式”，会遇到较高接受门槛：

- HR 已经习惯 ATS、招聘网站、Excel、邮件和协作工具。
- 企业招聘流程往往已经固化，不容易因为一个新工具整体迁移。
- HR 对 AI 判断天然会有信任成本。
- 招聘系统涉及候选人隐私、企业流程和合规要求，替换成本高。

因此，第一阶段不应试图替代传统工具，而应先成为 HR 现有流程的增强层。

## 3. 兼容策略

### 3.1 对候选人侧

候选人侧继续坚持人才画像闭环：

```text
简历上传 -> AI 访谈 -> 人才画像 -> 简历生成
```

但输出要兼容传统投递场景：

- ATS 友好简历。
- HR 阅读版简历。
- BOSS / 猎聘等平台可粘贴简介。
- 邮件投递正文。
- 一页候选人摘要。

### 3.2 对 HR 侧

HR 侧不要求一开始接受完整画像系统，而是先输出熟悉材料：

- 标准简历。
- 候选人摘要。
- Excel / CSV 候选人列表。
- 推荐理由。
- 风险点。
- 面试问题清单。
- 面试评价表。
- 可复制到 ATS 的候选人字段。

HR 可以继续使用原有工具，只把 AI Talent Agent 当作候选人理解和材料生成工具。

## 4. 需要兼容的工具类型

### 4.1 招聘渠道平台

这类工具解决“候选人从哪里来”：

- BOSS 直聘。
- 猎聘。
- 智联招聘。
- 前程无忧 51job。
- 拉勾等垂直招聘平台。

兼容方式：

- 生成适合平台粘贴的候选人简介。
- 生成平台友好的简历摘要。
- 支持用户手动导入来自这些平台的简历。
- 不做未经授权的数据抓取。

### 4.2 ATS / 招聘管理系统

这类工具管理招聘流程：

- 北森。
- Moka。
- 飞书招聘。
- 用友大易。
- 仟寻 MoSeeker。
- e 成科技。
- Greenhouse。
- Lever。
- Workday Recruiting。
- SmartRecruiters。
- iCIMS。
- Ashby。

MVP 阶段不做深度 API 集成，先做字段导出和复制。

兼容字段：

- 姓名。
- 手机。
- 邮箱。
- 当前公司。
- 当前岗位。
- 工作年限。
- 教育经历。
- 工作经历。
- 项目经历。
- 技能标签。
- 推荐理由。
- 风险点。
- 面试建议。

### 4.3 办公协作工具

这类工具是 HR 高频日常工作入口：

- 飞书。
- 企业微信。
- 钉钉。
- 微信。
- 邮件。
- Excel。

兼容方式：

- 生成可转发的候选人推荐卡片。
- 生成邮件正文。
- 生成飞书 / 企业微信 / 钉钉可读摘要。
- 导出 Excel / CSV。
- 生成面试官评价表。

## 5. 产品输出形态

### 5.1 候选人标准包

面向求职者：

- ATS 版简历。
- HR 阅读版简历。
- 平台简介。
- 邮件投递正文。
- 自我介绍。
- 岗位匹配建议。

### 5.2 HR 推荐包

面向 HR：

- 候选人一页摘要。
- 标准简历。
- 匹配分和分项得分。
- 推荐理由。
- 风险点。
- 建议面试问题。
- 面试评价表。

### 5.3 ATS 导入包

面向招聘系统：

- CSV / Excel 候选人表。
- 结构化 JSON。
- 标准字段映射。
- 附件简历。

## 6. 集成阶段

### Phase 1：导出兼容

目标：

- 不依赖第三方 API，也能进入 HR 工作流。

功能：

- 导出 PDF。
- 导出 Word。
- 导出 Excel / CSV。
- 复制候选人摘要。
- 复制推荐理由和面试问题。

这是优先级最高、成本最低、接受度最高的方式。

### Phase 2：协作工具兼容

目标：

- 进入 HR 日常沟通流程。

功能：

- 生成飞书/企业微信/钉钉可转发格式。
- 生成邮件格式。
- 生成面试官评价表。
- 生成候选人推荐卡片。

### Phase 3：ATS 字段映射

目标：

- 让 AI Talent Agent 输出可以被 ATS 使用。

功能：

- 标准候选人字段映射。
- 招聘系统导入模板。
- ATS 友好简历。
- 结构化 JSON 输出。

### Phase 4：API 集成

目标：

- 在产品验证后，再接入具体 ATS 或协作工具 API。

候选方向：

- 飞书招聘。
- Moka。
- 北森。
- 企业微信。
- 钉钉。
- Greenhouse。
- Lever。

API 集成不建议作为 MVP 起点。

## 7. 信任机制

HR 不一定会直接相信 AI 的判断，因此输出必须可解释。

每个推荐结论应包含：

- 结论。
- 证据。
- 置信度。
- 风险点。
- 建议面试验证问题。

不推荐：

> 候选人综合素质优秀，建议推荐。

推荐：

> 候选人在 XX 项目中负责需求拆解和跨团队推进，与岗位中“推动研发落地”的要求匹配；但数据分析能力只有技能标签，缺少项目证据，建议面试追问。

## 8. 合规和平台边界

必须避免：

- 未经授权抓取招聘平台数据。
- 未经候选人授权使用简历或访谈内容。
- 将候选人画像用于歧视性筛选。
- 将低置信度结论包装成确定事实。
- 把第三方平台或模板资源内置为自有资产。

建议：

- 用户主动上传或手动导入数据。
- 提供数据删除能力。
- 对候选人敏感信息做访问控制。
- 导出时明确数据来源和生成时间。

## 9. 对 MVP 的影响

这套兼容策略不会改变 MVP 的核心路线：

```text
简历解析 -> AI 访谈 -> 人才画像 -> 简历生成 -> 岗位匹配
```

但会改变产品交付重点：

- 不只展示“画像”，还要生成 HR 熟悉的材料。
- 不急着替换 ATS，先提供导出和复制。
- 不强迫 HR 进入新系统，先兼容 Excel、邮件和协作工具。
- 不把 AI 判断做成黑箱，所有推荐都带证据和面试验证问题。
